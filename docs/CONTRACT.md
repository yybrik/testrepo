# Gate contract v1

The proposed shared service is `cranelock.gate.v1.TrustedAccessGate`, defined in
`proto/cranelock_gate/v1/gate.proto`. Member 1 owns the eventual team-wide proto;
merge this service into that contract rather than maintaining incompatible copies.
Generated Python bindings are included in `cranelock_gate/generated`.

## Signing and identities

`SignedCommand` carries `payload_json` and an Ed25519 `signature`. The signed input is:

```text
UTF8("cranelock.command.v1") || 0x00 || payload_json
```

`payload_json` must be canonical ASCII JSON: keys sorted lexicographically, no spaces,
ASCII escapes for non-ASCII characters, no NaN/infinity, no duplicate keys. Signed
schemas use integers, strings, objects and arrays only; timestamps are integer Unix
milliseconds. `cranelock_gate.crypto.canonical` is the reference encoder. Sign raw
bytes, not base64 text. Public keys in configuration are 32-byte raw keys in hex;
command signatures are raw 64-byte signatures. Keys identify actors independently of
the gRPC connection. Mutual TLS authenticates the network and the gate's responses.

Each operation has exactly these common JSON keys, plus the fields listed below:

| Field | Value |
| --- | --- |
| `version` | Integer `1` |
| `lane_id` | Configured lane identity |
| `membership_id` | Configured fixed-membership identity |
| `request_id` | Globally unique string, 1-128 characters; UUID recommended |
| `actor_id` | Configured member/controller/simulator/operator identity |
| `operation` | Exact RPC method name |

Unknown/missing keys, noncanonical payloads, wrong domains and invalid signatures are
denied. Epochs, revisions and sequence numbers are nonnegative signed-64-bit-range
integers; only `expected_epoch` may be `-1` for first bootstrap.

## Operation fields and caller roles

| RPC | Additional keys | Authorised actor |
| --- | --- | --- |
| `InstallAuthority` | `certificate`, `expected_epoch`, `expected_revision` | Member for LOCAL; controller for CENTRAL |
| `TransferHolder` | `epoch`, `revision`, `destination` | Current holder |
| `RequestGrant` | `epoch`, `revision` | Current holder |
| `ValidateEntry` | `epoch`, `revision`, `holder`, `grant_id`, `session_id` | Trusted simulator only |
| `ReportLaneState` | `session_id`, `observation_revision`, `sequence`, `observed_at_ms`, `lane_state` | Trusted simulator only |
| `ClearLane` | `session_id`, `observation_revision`, `sequence`, `observed_at_ms`, `reason` | Trusted operator only |
| `GetState` | Empty protobuf request, no signed envelope | Read-only; authenticated channel in network deployment |

Example grant request:

```json
{"actor_id":"crane-1","epoch":0,"lane_id":"lane-1","membership_id":"group20-demo-v1","operation":"RequestGrant","request_id":"example-grant-1","revision":1,"version":1}
```

The gate alone chooses grant identifiers and expiry. Requests cannot supply a duration.
Configuration defaults: grant lifetime five seconds, observation freshness two seconds,
future timestamp allowance 250 ms. Simulator and gate clocks must be synchronised;
the observation limits are model assumptions, not a distributed-clock guarantee.

## Member 2: recovery certificate

`certificate` is an object with exactly `payload` and `signatures`.
The payload has exactly:

```json
{
  "version": 1,
  "lane_id": "lane-1",
  "membership_id": "group20-demo-v1",
  "epoch": 0,
  "mode": "LOCAL",
  "holder": "crane-1",
  "expected_epoch": -1,
  "expected_revision": 0
}
```

Each signature object contains `signer_id` and a base64-encoded `signature` over:

```text
UTF8("cranelock.authority.v1") || 0x00 || canonical(payload)
```

LOCAL requires at least `floor(N/2)+1` distinct configured member signatures. All supplied
signatures must verify over the same payload; duplicate and nonmember signers fail.
The next epoch must be exactly the gate's current epoch plus one. First local bootstrap
is epoch zero. Mode switches into LOCAL use a new majority-approved epoch too.

The certificate's expected epoch/revision must match both the outer command and the
gate's current authority. This prevents delayed recovery overriding an intervening
normal handoff. A rejected stale certificate must be regenerated by Member 2 against
fresh state; do not rewrite a signed certificate or reuse its request ID.

Member 2 remains responsible for persistent votes, crash/restart vote discipline and
ensuring members do not approve conflicting proposals. Gate verification does not
implement distributed consensus or prove that upstream voting is correct.

## Member 1: handoff and grant usage

Normal handoff does not increment epoch. The current holder signs `TransferHolder`
with the current epoch/revision and a different configured destination. The gate
requires a freshly confirmed CLEAR lane and no grant, increments the revision, and
returns the new holder. Wait for acknowledgement before permitting the new holder
to request a grant. On lost replies, reconcile using `GetState`.

Every accepted authority installation also increments revision. Grants bind to both
epoch and revision, so delayed same-epoch commands cannot survive a handoff.

`RequestGrant` atomically changes CLEAR to RESERVED and returns a grant:
`id`, `holder`, `epoch`, `revision`, `issued_at`, `expires_at`, `entered`.
The grant ID also becomes the lane session ID. Grant timestamps in responses are Unix
seconds; they are informational, and entry validity is always decided by the gate.

## Member 4: physical entry and occupancy

At the actual simulated entry boundary, the simulator calls `ValidateEntry` with the
holder and grant. It may admit a crane **only** when `allowed=true`,
`action_applied=true`, and `replayed=false`. This transition sets OCCUPIED atomically.
A crane itself cannot call entry validation. All simulator entry paths must use this
boundary; a previously issued grant alone never authorises movement.

The trusted physical model must serialise entry validation plus applying the movement,
exit processing, and observation sampling/clearance with one lane mutex. Keep that
mutex across the entry RPC and immediate physical-state update. No observer may report
the brief empty interval between accepted validation and applying movement as an exit.
Operator clearance must coordinate with this boundary and cancel any pending entry
actions before declaring the lane clear. On ambiguous RPC failure, perform no movement
and reconcile. A simulator that loses its physical state must report UNKNOWN rather
than initialise itself empty. These rules belong in Member 4's simulator integration.

Simulator updates use the current `session_id` and `observation_revision`, a globally
increasing observation `sequence`, and fresh `observed_at_ms`. Capture the revision
when sampling physical evidence, and never relabel old evidence with a new revision.
The revision changes on every lane phase transition and restart. In particular,
ValidateEntry changes it before returning: pre-entry observations cannot clear a
post-entry occupancy, even with tolerated timestamp skew. The simulator and operator share this sequence
space and must coordinate it or read the last sequence before sending updates.
Concurrent sequence collisions are safely rejected and require a new observation.

`lane_state` is CLEAR, OCCUPIED or UNKNOWN. A CLEAR report means independently
confirmed physical emptiness, not silence, timeout or loss of a token. CLEAR reports
while RESERVED are rejected because they may precede entry; the reservation is not
cancelled by a pre-entry position observation. Explicit operator clearance can revoke
that reservation after independently confirming safety.

After OCCUPIED, an authenticated CLEAR report confirms exit and removes the grant.
Missing updates make CLEAR/OCCUPIED UNKNOWN. Expired unentered grants make RESERVED
UNKNOWN. Timeout transitions require new evidence sampled after the uncertainty began;
increasing sequence numbers alone do not make an old observation fresh.

Restart creates a new reconciliation session ID. Old-session updates and entry
commands fail. Read current state and provide fresh physical confirmation after restart.
Recovery preserves the physical session so the previous occupant's trusted exit update
can still be processed, even when digital authority has changed.

The model trusts the simulator and operator to report reality accurately. If physical
position is unavailable, report UNKNOWN and block. Never synthesise CLEAR from grant
expiry, quorum success or crane disconnection.

## Member 5: controller and reconciliation

CENTRAL certificates use the same payload, but have exactly the controller's signature
and arrive in a controller-signed command. Initial central bootstrap is epoch zero.
Once initialised, controller updates must preserve the current epoch and match the
current expected revision. They increment revision and revoke outstanding grants.
Controller return cannot install an older epoch or reset occupancy.

Before returning to CENTRAL, read/reconcile gate state and the agent queue, then sign
the matching snapshot. Reconcile queues in Member 5/1 code; the gate does not schedule
or store them. Any concurrent authority change makes this update stale. Retry only
after rereading state and constructing a new signed update.

## Responses and retry semantics

`Decision` contains `allowed`, `reason`, `replayed`, `action_applied`, `request_id`,
`state_json`, and `grant_json`. State/grant JSON may include fractional Unix seconds.
They are response data, not signed command payloads. Use TLS outside loopback.

Request IDs are durably cached, including denials. Identical authenticated retries
return the original allowed/reason/grant, **current state**, `replayed=true` and
`action_applied=false`. Original success is historical; it does not resurrect a revoked
grant, reconfirm a cleared lane, reinstall authority or authorise movement. A different
payload using the same ID gets `REQUEST_ID_CONFLICT`. New attempts after a denial need
new IDs. Cached state is deliberately refreshed so restarts cannot hide fencing state.

Transport timeout/unavailability means no movement. An entry reply lost after commit
may leave the gate OCCUPIED while the simulator has not entered. Reconcile and obtain
fresh physical clearance; never infer permission from a retry. This conservative rule
sacrifices availability to avoid duplicate movement after ambiguous replies.

Common reasons: `OK`, `STATE`, `INVALID_REQUEST`, `INVALID_SIGNATURE`, `UNAUTHORIZED`,
`INVALID_CERTIFICATE`, `NO_QUORUM`, `AUTHORITY_CONFLICT`, `STALE_EPOCH`, `UNKNOWN_EPOCH`,
`STALE_REVISION`, `WRONG_HOLDER`, `INVALID_HOLDER`, `LANE_UNKNOWN`, `LANE_BUSY`,
`INVALID_GRANT`, `EXPIRED_GRANT`, `ALREADY_ENTERED`, `OUTSTANDING_GRANT`, `STALE_SESSION`,
`STALE_OBSERVATION`, `REQUEST_ID_CONFLICT`, `CLOCK_ROLLBACK`, `STORAGE_UNAVAILABLE`.

## Reconciliation state and events

`GetState` returns authority (`epoch`, `mode`, `holder`, `revision`), lane state, current
grant, physical session ID/revision, last observation sequence/time, observation freshness
barrier, clock watermark and cumulative safety-stop duration. Initial epoch is `-1`
and initial lane state is UNKNOWN. Reading state also runs timeout maintenance.

SQLite stores a durable ordered event stream alongside decisions. Export JSONL using
the server CLI. Each event contains `event_id`, timestamp, operation, request ID,
decision/reason, replay flag, epoch/revision, holder, lane state, session and grant ID.
For entry counts, count accepted ValidateEntry events **excluding replayed events**.
Unauthenticated malformed envelopes are counted in server metrics but are not stored
in the durable authenticated-request audit table. Member 4 should combine gate events
with simulator physical-entry/exit traces; gate logs alone do not prove physical safety.
